## 1 Цепочка поставки

| Шаг | Что проверяется или создаётся | При провале |
|---|---|---|
| Чистая установка | Node 24, `npm ci` из зафиксированного lock-файла | Исправить состояние источников и повторить проверку |
| Стиль и статический анализ | ESLint, предупреждения считаются ошибками | Исправить правило или код с понятным основанием |
| Регрессия | 15 Node-тестов. Ветвление, карточки, календарь и API аккаунтов | Сборка релиза не продвигается |
| Сборка | Vite создаёт `dist` со статическим интерфейсом | Восстановить сборку или вернуться к проверенному коммиту |
| Пакеты | `npm audit --audit-level=high` и Trivy, линейки High/Critical | Блокировать публичную выкладку по известным существенным находкам |
| Артефакт и выпуск | Передача `dist` в publish. Для PR выполняется проверка. Для main можно публиковать | Проверить журнал среды github-pages, пользователи сохраняют предыдущую опубликованную версию |

Внешние Actions закреплены SHA. Контекст проверки ветки называется `Verify Til Mix`. Проверка имеет чтение исходников. Выкладке выделены `pages: write` и `id-token: write`. В файле нет платного ключа. Сборка и сканирование прошли, отдельное действие publish завершилось успешно. [Прогон](https://github.com/Ameke111/til-mix/actions/runs/43741667460)

**Защита ветки.** У main создано правило GitHub с pull request и проверкой `Verify Til Mix`. Force push и удаление ветки запрещены обычным участникам. Обязательные человеческие approvals отключены для индивидуального проекта. Владелец сохранил штатное право административного обхода. В обычной работе автор открывает PR, читает собственный diff и проверяет результат CI. Если появится внешний ревьюер, язык и доступ к данным выносятся на независимую проверку. ## 2 Четыре метрики курса

Снимок содержит события окружения `github-pages` на 15 ноября. `success` берётся из статусов конкретного Deployment. Предыдущая активная версия может стать `inactive` после замены. Это не ошибка. Время от коммита берётся от даты коммитера SHA, указанного в Deployment. В выборке есть коммиты документации, которые тоже инициировали сборку.

| Метрика | Расчёт и факт | Оценка применимости |
|---|---|---|
| Deployment Frequency | 10 успешных выкладок за один наблюдаемый календарный день | Активная автоматизированная поставка в день наблюдения. Недельного или месячного уровня выборка не устанавливает |
| Lead Time for Changes | От времени коммита HEAD до первого статуса success. **P50 0,60 мин**, **P85 0,77 мин** | На данном стеке автоматическая публикация быстрая. Показатель не включает подготовку, ревью и пилот |
| Change Failure Rate | 0 подтверждённых нарушений сервиса после 10 выкладок в доступном журнале, наблюдаемая доля 0/10. Попыток с финальным failure/error в Deployment-снимке нет | Нулевая наблюдаемая доля без внешнего мониторинга. Реальный CFR пока не оценён надёжно |
| Time to Restore Service | Медиана интервалов подтверждённых инцидентов. Пар начала и восстановления в журнале нет | **Н/Д**. Нужен зафиксированный инцидент либо отдельно помеченная пробная репетиция |

Текущие определения DORA могут отличаться от четырёх метрик учебной рубрики. В отчёте сохранены названия и расчёт, привязанные к методичке, а выводы ограничены наблюдаемой выборкой. [DORA](https://dora.dev/guides/dora-metrics/) · [GitHub Deployments API](https://docs.github.com/en/rest/deployments/deployments)

## 3 Два улучшения

1. **Связать релизы с проверками доступности.** Добавить после Pages один анонимный smoke: открыть главную и конкретный урок, сохранить URL выкладки и время успеха. Для следующих пяти релизов цель 5/5 отметок. Тогда сигнал о неработающей выкладке появится в проверке релиза, а журнал можно будет связать с восстановлением. Локальное допущение: сигнал в первые 5 минут после выкладки.
2. **Отделить изменения сайта от курсовых документов в измерении.** При сборе отчёта помечать SHA как feature/content/docs. Цель — классифицировать все следующие 10 коммитов до расчёта частоты. Это позволит отдельно увидеть выкладки, которые меняют пользовательские действия, сохранив общую таблицу прозрачной.

## 4 Релиз и откат

| Этап | Условия и ответственный |
|---|---|
| Окно | Плановое окно раз в неделю вечером по времени Казахстана. Срочные исправления блокирующих ошибок допускаются отдельно. Согласование с пользователями требуется перед реальным пилотом |
| Перед PR | Ameke111 заполняет критерии и ссылку GitHub, проверяет scope и отсутствие файлов SQLite/секретов |
| Перед слиянием | Посмотреть diff и результат Verify Til Mix. Для интерфейса открыть гостевой профиль и пройти одну историю. Для API проверить два аккаунта на изолированной базе |
| После выкладки | Проверить URL Pages, гость открывает урок, получает карточку и может скачать прогресс, статическая версия не показывает активную регистрацию |
| Триггер отката | Гость не может начать урок, новая версия повреждает запись, блокирует основную форму или CI выпустил неверный артефакт |
| Первый шаг | Отметить время и SHA в issue, зафиксировать проявление и не выкладывать новые функции до проверки |
| Откат Pages | Найти последний успешный SHA и отменить соответствующее изменение через revert PR. После Verify Til Mix и merge снова проверить ссылку и основной путь |
| Откат Node | Сохранить отдельную копию текущего SQLite. Поднять предыдущую сборку на отдельном порту с тестовой базой, проверить чтение и форму. Для несовместимой структуры применять подтверждённую копию в соответствии с RPO/RTO |
| Закрытие | Сохранить время обнаружения и восстановления, отметку вернувшейся версии и владельца следующего действия. Для учебной репетиции пометить тип события «test» |

Операция восстановления в этом документе — проверяемый сценарий на следующую работу, фактический производственный сбой в выборке отсутствует. Источник для дашборда фиксируется в JSON. Запуск `python course/delivery-metrics.py` воспроизводит графики, `--refresh` использует актуальные события GitHub. Codex применялся для черновика отчёта и скрипта.
